CsAgent et FlowPortal

CsAgent est un agent autonome qui travaille dans votre dossier avec le modèle de langage de votre choix. FlowPortal enchaîne des tâches décrites dans un fichier, des workflows, et appelle CsAgent quand il faut lire, comprendre ou rédiger. Cette page présente les deux outils, la façon dont ils s'utilisent ensemble et où trouver la documentation.

Les deux outils

CsAgent

Un agent de codage autonome pour Windows, Linux et macOS. Il comprend une demande en langage naturel, lit et modifie vos fichiers, lance des commandes, et demande votre accord avant d'écrire, de déplacer ou de supprimer quoi que ce soit. Il utilise une API compatible OpenAI, par exemple l'API Albert.

  • Trois interfaces : terminal (TUI), web et légère (Lean UI), plus un mode API (--api) pour les autres programmes.
  • Une demande unique en ligne de commande : csagent --prompt "…".
  • Des skills : des fichiers Markdown qui lui apprennent une tâche récurrente, sans recompiler.
  • Des outils supplémentaires par MCP, et une mémoire entre les sessions.

FlowPortal (CSFlow)

Un portail local où chaque workflow est une carte : on le lance en un clic, on lit et on modifie son YAML, on retrouve le résultat de chaque lancement. Il repose sur le moteur de CSFlow : « Workflows orchestrés en Python, propulsés par CSAgent ».

  • Un workflow est un fichier YAML : une liste d'étapes exécutées dans l'ordre, avec des branches possibles.
  • Onze types d'étape, dont agent (CsAgent lit et rédige), python, shell et human_approval (l'humain décide).
  • Livré aussi sous forme d'exécutable (FlowPortal.exe) : aucun Python à installer.
  • Un mode MCP (FlowPortal --mcp) qui permet à CsAgent de lancer vos workflows.

Le principe de conception de CSFlow : Python orchestre, l'IA lit et rédige, l'humain décide. Les chiffres se calculent en code, jamais « à l'intuition » du modèle.

Premiers pas

  1. Obtenir une clé d'API pour un serveur compatible OpenAI, par exemple l'API Albert, et la définir : set ALBERT_API_KEY=votre-cle (Windows) ou export ALBERT_API_KEY=votre-cle (Linux, macOS).
  2. Essayer CsAgent seul : csagent --ui, puis ouvrir http://localhost:5050. Ou, sans interface : csagent --prompt "bonjour".
  3. Essayer FlowPortal : FlowPortal.exe (ou python app.py depuis les sources), puis lancer la carte demo_report.
  4. Les relier : start_csagent.bat ou ./start_csagent.sh, depuis le dossier de FlowPortal, puis demander à CsAgent « liste les workflows ».

Lancez toujours CsAgent depuis le dossier de FlowPortal : les chemins des workflows sont relatifs à ce dossier, et c'est aussi là que CsAgent cherche ses skills.

À savoir

  • Validation humaine : un workflow qui contient une étape human_approval ou user_input ne peut pas être lancé par MCP ni avec --workflow. Ouvrez-le dans le portail.
  • Un seul workflow à la fois. Seuls les fichiers du dossier workflows/ sont accessibles par MCP.
  • Port 8080 : --workflow démarre son propre serveur sur ce port. Ne lancez pas en même temps le worker de start_csagent.
  • Étapes shell et python : elles ne passent pas par le filtre de commandes de CsAgent. Relisez un workflow avant de le lancer, surtout s'il a été écrit par un modèle.

Le problème

Les tâches répétitives prennent du temps, et copier-coller entre vos fichiers et un assistant IA ne tient pas dans la durée. Trois frustrations reviennent :

  • L'assistant ne voit pas votre travail. Vous copiez un texte, il répond, vous recopiez le résultat dans le bon fichier.
  • Un script classique est rigide. Dès qu'il faut comprendre un document ou rédiger un compte rendu, il ne sait plus faire.
  • Laisser une IA agir seule inquiète. Que va-t-elle modifier, déplacer, supprimer ?

CsAgent et FlowPortal répondent à ces trois points : un agent qui travaille dans votre dossier, des workflows qui fixent le cadre, et un humain qui garde la décision.

CsAgent : un agent qui travaille dans votre dossier

Vous décrivez la tâche en français, CsAgent la fait pas à pas dans votre dossier et vous demande votre accord avant d'écrire, de déplacer ou de supprimer quoi que ce soit.

  • Il agit, il ne se contente pas de répondre. Il lit vos fichiers, les modifie, lance des commandes et vérifie le résultat.
  • Le modèle de votre choix. Il utilise n'importe quel serveur compatible OpenAI, par exemple l'API Albert. Pas d'abonnement imposé à un fournisseur.
  • Partout. Windows, Linux et macOS, en terminal, dans le navigateur ou en interface légère, et un mode API pour les autres programmes.
  • Il apprend vos habitudes. Un skill est un simple fichier Markdown qui lui explique une tâche récurrente : pas de code, pas de recompilation.
  • Une seule commande pour une seule demande. csagent --prompt "..." répond puis quitte : la sortie se redirige vers un autre programme.

FlowPortal : des workflows qu'on peut relancer et relire

FlowPortal transforme une tâche en workflow : un fichier YAML qui liste les étapes, relançable en un clic, où chaque étape a un rôle clair. Le principe : Python orchestre, l'IA lit et rédige, l'humain décide.

  • Reproductible. La même tâche se relance à l'identique. Chaque lancement garde son dossier de sortie, nommé d'après le workflow et l'heure.
  • Chaque outil à sa place. Les calculs exacts (totaux, dates) passent par du code, jamais par l'intuition du modèle. L'IA intervient seulement là où il faut lire, comprendre ou rédiger.
  • L'humain garde la main. Une étape de validation arrête le workflow tant que quelqu'un n'a pas approuvé ou refusé.
  • Lisible. Le YAML se lit, se modifie et se partage ; le portail l'affiche en cartes, avec le résultat de chaque lancement.
  • Sans installation de Python. L'exécutable FlowPortal.exe embarque tout le nécessaire.

Pourquoi leur faire confiance

Vous gardez le contrôle à chaque niveau, et vous pouvez vérifier ce qui se passe.

  • Votre accord avant d'agir. Toute écriture, tout déplacement et toute suppression de CsAgent attendent votre confirmation, sauf si vous choisissez explicitement de la donner d'avance (--yes).
  • Le modèle ne touche jamais le disque lui-même. Il demande un outil ; CsAgent vérifie la demande, vous consulte quand c'est important, puis l'exécute.
  • Une décision humaine dans le workflow. Une étape human_approval place la validation entre l'IA et toute action qui engage.
  • Libre et sans dépendance cachée. CsAgent est sous licence MIT, écrit en C# et sans paquet NuGet. FlowPortal publie aussi son code.
  • Des tests. CsAgent compte 366 tests automatisés à la version 0.9.23, et chaque version a sa note publique.

Démarrer en quinze minutes

  1. Obtenir une clé d'API d'un serveur compatible OpenAI (l'API Albert, par exemple) et la définir : set ALBERT_API_KEY=votre-cle sous Windows, export ALBERT_API_KEY=votre-cle sous Linux et macOS.
  2. Essayer CsAgent seul : csagent --ui, puis ouvrir http://localhost:5050. Demandez-lui de lister les fichiers du dossier et de résumer l'un d'eux.
  3. Essayer FlowPortal : lancer FlowPortal.exe et exécuter la carte demo_report.
  4. Les relier : depuis le dossier de FlowPortal, lancer start_csagent.bat (ou ./start_csagent.sh) et écrire « liste les workflows ».
  5. Automatiser : csagent --mcp-config mcp.json --workflow demo_report.

Lancez toujours CsAgent depuis le dossier de FlowPortal : c'est là qu'il trouve les workflows et ses skills.

Pour qui, et ce que ces outils ne font pas

Ils conviennent à ceux qui veulent qu'une tâche soit faite, plutôt qu'une conversation à son sujet : développeurs, équipes techniques, et toute personne qui répète les mêmes opérations sur des fichiers, des données ou des rapports.

Quelques limites à connaître avant de s'engager :

  • Il faut une clé d'API pour un modèle : CsAgent n'en fournit pas.
  • Un workflow avec une validation humaine ne se lance pas depuis la ligne de commande ni par un agent : il s'ouvre dans le portail.
  • Un seul workflow s'exécute à la fois.
  • CSFlow n'a ni boucle native, ni exécution en parallèle, ni sous-workflow : on contourne avec un script Python ou plusieurs étapes.
  • Les étapes shell et python d'un workflow ne passent pas par le filtre de commandes de CsAgent : relisez un workflow avant de le lancer, surtout s'il a été écrit par un modèle.

Guide d'utilisation de CsAgent

Décrivez la tâche. CsAgent lit vos fichiers, lance des commandes et modifie le code pas à pas, avec le modèle de langage que vous choisissez. Toute écriture, tout déplacement et toute suppression attendent votre accord.

Libre et gratuit (MIT). Fonctionne sous Windows, Linux et macOS. Aucun paquet NuGet.

Ce qu'il y a dans la boîte

Il demande d'abord

Chaque écriture, déplacement, suppression, commit, e-mail et appel MCP attend un oui. Les étapes en lecture seule s'exécutent librement.

Trois façons de lui parler

Le terminal, une interface web, ou une page web légère façon terminal. Même agent, même mémoire.

Le bon modèle, à chaque message

Code, chat et images vont chacun au modèle qui convient, affiché sous chaque réponse, et réglable en JSON. L'API Albert par défaut, ou tout serveur compatible OpenAI, Ollama compris.

Il se souvient

Ce qui a échoué et ce qui a marché survit à la troncature de l'historique, et un court résumé des décisions et du travail restant passe à la session suivante.

43 outils intégrés

Fichiers, shell, git, web, courrier et agenda Outlook, Excel, audio et presse-papiers. En ajouter un tient en six étapes.

Voix et images

Dictez une tâche ou joignez une capture d'écran. Les longs enregistrements sont acceptés.

Pilotable par du code

Un serveur sans interface diffuse chaque étape sous forme d'événements. Conçu pour les orchestrateurs et les scripts.

Un seul fichier à lancer

Se publie en un exécutable natif unique. Aucun paquet NuGet à l'intérieur, rien à installer à côté.

Chaque action passe par la même porte

Le modèle ne touche jamais votre disque lui-même. Il demande un outil. CsAgent vérifie la demande, vous consulte quand c'est important, l'exécute, puis renvoie le résultat.

  1. Vous décrivez une tâche

    En langage courant, au clavier, à la voix ou avec une image.

  2. Le modèle propose une étape

    Il explique ce qu'il pense et choisit un outil, comme search_files ou write_file.

  3. CsAgent la contrôle

    • Les chemins de fichiers doivent rester dans le dossier de travail.
    • Les commandes shell passent un filtre contre les motifs dangereux.
    • Les outils destructifs s'arrêtent et vous demandent.

  4. L'outil s'exécute

    Une commande shell est interrompue après 60 secondes. Le résultat repart vers le modèle.

Le modèle lit le résultat et propose l'étape suivante. Il s'arrête quand la tâche est terminée, ou après 30 étapes. Une étape qui échoue n'est pas répétée à l'aveugle : l'erreur et ce qui a marché ensuite sont gardés en mémoire.

Au clavier

Pour ceux qui veulent qu'une tâche soit faite, pas une conversation à son sujet.

Choisissez la fenêtre qui vous convient

Vous préférez rester dans le shell ? csagent seul lance la session dans votre terminal, comme dans le rejeu ci-dessus. Pour une seule demande, sans session : csagent --prompt "hello my name is John" exécute la demande et rend la main (code de sortie 0, ou 1 en cas d'erreur). Seule la réponse est écrite sur la sortie standard, sans bannière ni étapes : elle peut être redirigée vers une autre commande, et les erreurs vont sur la sortie d'erreur. --verbose rend l'affichage complet.

Parlez-lui

Appuyez sur le micro dans l'interface web ou lean et parlez. L'audio est enregistré par morceaux de 30 secondes pendant que vous parlez : un onglet fermé par erreur vous coûte au plus la dernière demi-minute.

À l'arrêt, CsAgent transcrit tout l'enregistrement avec Whisper et vous choisissez : utiliser le texte comme instruction, ou le garder dans un fichier joint à votre prochain message. Un sélecteur FR / EN / Auto à côté du bouton indique la langue parlée.

La transcription a lieu après l'arrêt, pas en direct. Au-delà de quelques minutes, ffmpeg est nécessaire. L'audio part vers votre point d'accès configuré : choisissez un point d'accès local s'il ne doit pas quitter la machine.

Un orchestrateur peut envoyer son propre enregistrement en mode --api, sans interface : c'est ainsi que CSFlow permet de dicter un texte dans un workflow.

Il se souvient de ce qu'il a déjà essayé

Une longue tâche chasse les anciens messages du contexte du modèle, et un agent qui oublie répète ses erreurs. CsAgent garde deux couches de plus sur disque et réinjecte les leçons pertinentes avant chaque appel au modèle.

  • La mémoire exacte conserve les 50 dernières étapes telles quelles : réflexions, appels, erreurs, réussites.
  • La mémoire sémantique conserve jusqu'à 200 leçons étiquetées, par exemple une erreur et le remède qui a marché. Elle retient les arguments d'un appel, pas son résultat.
  • Le résumé de session : à la fin d'une exécution, le modèle la condense en quatre courtes listes. La session suivante part de là. --no-distill évite ce dernier appel au modèle.
  • La compression de la conversation : quand l'historique grossit (les deux tiers de --context-chars par défaut), un résumé de 300 mots remplace les anciens messages et reste enregistré avec la conversation. --compress-threshold <n> règle le seuil, --no-compress la désactive.
  • L'archive : les messages résumés ou retirés du contexte ne sont plus perdus. Ils sont ajoutés à archive.jsonl, et l'outil recall y retrouve le texte exact (décisions, erreurs, commandes) par mots-clés, en français et en anglais.

Chaque projet a sa propre mémoire, appelée session, avec --session nom (ou --mem nom). C'est un dossier de JSON ordinaire, que vous pouvez lire, modifier ou supprimer. Elle est reprise automatiquement au lancement suivant. À l'invite, .session, .list, .save [nom], .use nom, .compress, .empty et .delete nom la gèrent. Avec --no-save, rien n'est écrit : la session est jetable.

Réglages

--verbose
Avec --prompt : affiche la bannière, les étapes, les appels d'outils et les jetons. Par défaut, --prompt n'écrit que la réponse, pour pouvoir la rediriger.
--quiet
N'affiche que les messages de l'assistant, les avertissements et la ligne finale. Un appel en échec garde une ligne, et une action destructive montre son appel juste avant de demander.
--dry-run
Simule l'exécution des outils sans rien modifier.
--yes
Approuve tous les appels d'outils automatiquement. Les filtres de chemins et de commandes restent actifs.
--mem nom
Choisit le dossier de mémoire, un par projet ou par tâche.

Des garde-fous que vous pouvez lire

L'autonomie n'a de sens que si vous pouvez prévoir le pire cas. CsAgent garde ses règles peu nombreuses, et dans du code lisible.

  • Il demande d'abord

    write_file, edit_file, delete_file, move_file, unzip, git_commit, git_pull, git_push, git_checkout, download_file, send_email, create_appointment, save_attachment, group_msg_by_sender, write_clipboard et tout appel MCP s'arrêtent et attendent votre réponse. --yes supprime la question, et rien d'autre.

  • Un dossier, pas un disque

    Les outils de fichiers sont limités au dossier de travail et à ses sous-dossiers. La seule exception volontaire concerne les pièces jointes d'e-mail, et l'envoi demande d'abord. Lancez CsAgent dans le projet, pas dans votre dossier personnel.

  • Un filtre pour les commandes risquées

    Les commandes shell sont contrôlées avant exécution, avec une liste par plateforme : sudo, chmod, dd, mkfs, shutdown et les dossiers système sous Linux et macOS ; format, del /f, rd /s, reg delete, net user, diskpart et runas sous Windows.

  • Des limites

    Une commande est interrompue après 60 secondes. Un fichier de plus de 500 Ko n'est pas lu en entier ; l'agent doit le parcourir avec grep ou head.

  • Des données, pas des ordres

    Les e-mails, les transcriptions et les résultats MCP viennent de l'extérieur. Le prompt système demande au modèle de les traiter comme des données et de ne jamais suivre les instructions qu'ils contiennent.

  • Un essai à blanc

    --dry-run montre ce que l'agent ferait, sans le faire.

Un garde-fou n'est pas un bac à sable

Le filtre du shell repose sur des motifs, et aucune liste n'attrape tout. Pour un travail sans surveillance, lancez CsAgent dans un dossier jetable ou un conteneur, et gardez les approbations actives.

Ce qui quitte votre machine

Vos messages, les fichiers et sorties de commandes que l'agent lit, et les résultats de ses outils partent vers le point d'accès que vous avez configuré. L'audio aussi, quand vous le transcrivez. web_search interroge DuckDuckGo, et fetch_url et http_request contactent les adresses que vous demandez. CsAgent n'a ni télémétrie ni serveur à lui. Avec un point d'accès local, rien d'autre ne sort.

Une exception à connaître : les deux interfaces web chargent quelques bibliothèques et polices depuis des CDN publics à l'ouverture de la page, donc le navigateur a besoin d'un accès à Internet pour les afficher comme prévu.

Dans votre architecture

Un seul processus, une petite surface. Vous pouvez le piloter, l'étendre, et le lire en entier.

Pilotez-le en HTTP

--api lance le même serveur que l'interface web, sans aucune interface : ni pages, ni navigateur, ni presse-papiers. Il diffuse chaque étape en Server-Sent Events, pour qu'un autre programme, un orchestrateur par exemple, puisse suivre et répondre.

csagent --api --yes
curl -N "http://localhost:5050/api/chat?prompt=List+every+TODO+into+TODO.md"

Depuis Python : le dépôt fournit un client en bibliothèque standard seule, python/csagent_client.py (aucune dépendance à installer).

  • Sans --yes, un appel destructif émet un événement confirm et attend POST /api/confirm avec un corps true ou false.
  • Pour écouter au-delà de localhost, une clé est obligatoire (--api-key ou CSAGENT_API_KEY), envoyée en Authorization: Bearer ou X-API-Key. Sans clé, un --host non local est refusé au démarrage.
  • Un serveur porte une seule conversation. Pour des tâches en parallèle, lancez une instance par tâche, chacune avec son --mem et son --port.
  • POST /api/chat accepte du multipart/form-data avec une image facultative.
  • La transcription est aussi disponible en HTTP : POST /api/audio/start, POST /api/audio/{id} (les octets de l'audio), puis POST /api/audio/{id}/transcribe (flux SSE progress, done ou error). Même clé d'API, mêmes conditions que la dictée.

Lancez un workflow CSFlow

--workflow exécute un workflow de CSFlow depuis la ligne de commande, sans passer par le modèle : pas de jeton dépensé, et un code de sortie utilisable dans un script.

csagent --mcp-config mcp.json --workflow demo_report

Le mcp.json est celui de CSFlow : CsAgent y cherche le serveur MCP nommé csflow (FlowPortal.exe --mcp) et le démarre.

  • CsAgent démarre aussi son serveur --api (port 8080) pour les étapes agent du workflow. Ne le lancez pas si un worker occupe déjà ce port.
  • Chaque étape s'affiche quand elle se termine. Code de sortie : 0 terminé, 1 échec ou Ctrl+C, 2 non démarré.
  • Les workflows avec une étape human_approval ou user_input sont refusés par CSFlow : lancez-les depuis son interface.
  • Les étapes agent utilisent la mémoire csflow_worker, sans distillation ; --fresh la vide au départ.

Le bon modèle pour chaque message

CsAgent choisit le modèle message par message, sans appel supplémentaire ni délai. Trois profils :

  • Code (deepseek-v4-flash) : le code, les fichiers, le shell, git, le courrier, l'audio. C'est lui qui exécute les outils.
  • Chat (openweight-large) : les recherches (web, actualités, météo, un lien à lire) et les questions générales.
  • Vision (gemma-4-31b-it) : dès qu'une image est jointe ou déjà dans la conversation.

Le modèle est affiché avant chaque exécution, avec la raison du choix, et sous chaque message de l'assistant (dans le terminal, dans les interfaces web et dans l'événement model de l'API). --model <nom> impose un seul modèle, et --no-route revient au modèle de code partout.

> User: cherche sur internet les actualités de l'IA
  [model: openweight-large (chat: recherche web (« actualites »))]
...
  [model: openweight-large]

csagent --explain-routing "open in Edge browser"
Modèle  : deepseek-v4-flash
Raison  : action sur votre ordinateur (« open »)

Sur un point d'accès personnalisé (Ollama…), il n'y a pas de modèle de chat tant que vous n'en indiquez pas un avec --chat-model : tous les messages utilisent alors le modèle de code. Le modèle de chat doit gérer l'appel d'outils.

Réglez le routage à la main

csagent --init-routing crée un dossier LLMRoutingRules/ de fichiers JSON. Modifiez-les avec un éditeur : le changement s'applique au message suivant, sans redémarrage ni recompilation.

  • models.json : le modèle de chaque profil (null pour garder la valeur intégrée).
  • keywords.json : ajouter ou retirer des mots, des expressions et des extensions de fichier.
  • rules.json : vos règles, testées avant la logique intégrée, la première qui correspond l'emporte.

Une erreur dans un fichier n'arrête jamais l'agent : un avertissement s'affiche une fois et les valeurs intégrées restent en place. --explain-routing "message" montre le modèle qui serait choisi, sans appeler aucun modèle. Les messages de routage existent en français et en anglais (--lang fr|en, ou la langue du système).

Le dossier est cherché dans l'ordre : --rules <dossier>, puis ./LLMRoutingRules, puis à côté de l'exécutable.

Apportez votre modèle

CsAgent parle l'API de chat compatible OpenAI, avec appel d'outils. Il utilise par défaut l'API Albert, le service de LLM du secteur public français, et fonctionne avec tout ce qui expose la même interface.

Choisissez un modèle qui gère l'appel d'outils, car la boucle de l'agent en dépend. Les images demandent un modèle de vision, indiqué par --vision-model ; le modèle du code et celui du chat se règlent avec --code-model et --chat-model.

ollama pull qwen2.5-coder:14b
csagent --endpoint http://localhost:11434/v1 --model qwen2.5-coder:14b

Un point d'accès local n'a pas besoin de clé. Un point d'accès distant lit ALBERT_API_KEY. Définissez CSAGENT_ENDPOINT pour ne plus retaper l'URL. Les limites de débit (HTTP 429) sont retentées avec temporisation, réglable par --max-retries et --retry-delay.

Branchez un serveur MCP

En HTTP (--mcp) ou en local (--mcp-stdio), un ou plusieurs serveurs, avec des en-têtes d'authentification. Leurs outils sont proposés au modèle à côté des outils intégrés.

  • Les outils apparaissent sous le nom mcp_<nom> (ou mcp_<serveur>_<nom> avec plusieurs serveurs), donc un serveur ne peut jamais remplacer un outil intégré.
  • Un serveur en panne donne un avertissement ; les autres restent utilisables. Les secrets des en-têtes (${VAR}) ne sont jamais affichés.
  • CsAgent ne peut pas savoir ce que fait l'outil d'un serveur, donc chaque appel MCP demande votre accord.
  • Ce qu'envoie un serveur est traité comme une donnée non fiable.
csagent --mcp https://api.exemple.com/mcp \
  --mcp-header "Authorization: Bearer ${MCP_TOKEN}"
csagent --mcp-stdio "npx -y @modelcontextprotocol/server-filesystem ."

Limites actuelles : outils seulement (ni ressources ni prompts), pas d'OAuth, résultats en texte. Rien n'est lancé automatiquement depuis le dossier de travail : un serveur stdio ne démarre que si vous le nommez.

  1. Ajoutez un cas au switch de DispatchAsync.
  2. Décrivez l'outil dans ToolDefinitions, sous forme de schéma de fonction JSON.
  3. Écrivez le gestionnaire. Il renvoie OK: … ou Error: ….
  4. Contrôlez les chemins avec IsSafePath et les commandes avec IsSafeCommand.
  5. S'il modifie des choses, ajoutez-le à IsDestructive pour qu'il demande d'abord.
  6. S'il a besoin d'un rappel de l'hôte, passez un délégué à DispatchAsync.

Gestion des erreurs 429

Une réponse HTTP 429 veut dire que le serveur LLM (Albert par exemple) refuse la requête parce qu'une limite est atteinte. CsAgent distingue une limite qui se lève toute seule en quelques secondes d'une limite journalière qui ne se lève qu'à la remise à zéro, et ne réagit pas de la même façon.

Ce qui se passe, dans l'ordre

  1. La requête part vers le serveur (/chat/completions).
  2. Si le serveur répond 429, CsAgent lit le texte de la réponse pour savoir de quelle limite il s'agit (voir la section suivante).
  3. Limite par minute ou non reconnue : CsAgent attend, puis renvoie la même requête, jusqu'au nombre maximal de tentatives.
  4. Limite journalière : aucune nouvelle tentative, car attendre ne servirait à rien. CsAgent passe à un autre modèle si c'est possible, sinon il s'arrête avec un message.
  5. Toute autre erreur HTTP (401, 500…) n'est jamais réessayée : elle est affichée tout de suite.

Reconnaître le type de limite

CsAgent cherche des mots dans le corps de la réponse 429, sans tenir compte des majuscules.

Mots trouvésTypeRéaction
per day, per_day, daily, (tpd), (rpd)JournalièrePas de nouvel essai, bascule de modèle
per minute, per min, per_minute, (tpm), (rpm)Par minuteNouvel essai avec attente
aucun de ces motsNon reconnueTraitée comme une limite par minute

Si les deux familles de mots apparaissent, la limite journalière l'emporte. Exemple de réponse d'Albert : {"detail":"1280000 input tokens per day exceeded (remaining: 0)."}

Le délai entre deux essais

  • Si le serveur envoie l'en-tête Retry-After (en secondes ou sous forme de date), CsAgent attend ce délai.
  • Sinon, le délai double à chaque essai : délai de base × 2^(essai − 1).
  • Dans les deux cas, l'attente est plafonnée à 70 secondes.

Avec les valeurs par défaut (6 tentatives, 1 000 ms de délai de base), il y a cinq attentes : 1, 2, 4, 8 et 16 secondes, soit environ 31 secondes au total avant d'abandonner.

Réglages en ligne de commande

OptionDéfautEffet
--max-retries <n>6Nombre total de tentatives, première requête comprise. 1 désactive toute nouvelle tentative
--retry-delay <ms>1000Délai de base avant la première nouvelle tentative, en millisecondes

Ces deux options valent pour tous les modes : terminal, interface web, Lean UI et mode --api.

  • Une valeur absente, non numérique, nulle ou négative est ignorée sans message : la valeur par défaut s'applique.
  • --retry-delay ne peut pas dépasser 70 000 (le plafond). Au-delà, la combinaison est refusée.
  • Le facteur de doublement (2) et le plafond (70 s) ne se règlent pas en ligne de commande.

Quota journalier épuisé : la bascule de modèle

Quand la limite est journalière, CsAgent ne perd pas la requête : il la renvoie à un autre modèle et poursuit la tâche, avec un message d'avertissement.

Quel modèle est choisi

  1. Celui de la variable d'environnement CSAGENT_FALLBACK_MODEL, si elle est définie.
  2. Sinon, le modèle de code (deepseek-v4-flash par défaut, ou la valeur de --code-model), uniquement sur l'endpoint Albert par défaut. Sur un autre --endpoint, ce nom ne veut rien dire : il n'y a alors pas de bascule automatique.
Valeur de CSAGENT_FALLBACK_MODELEffet
un nom de modèleBascule vers ce modèle

(non définie)Règle 2 ci-dessus

Règles de sécurité

  • Au plus 2 bascules par exécution.
  • Pas de bascule si la conversation contient une image : l'autre modèle ne saurait peut-être pas la lire.
  • Pas de bascule vers le modèle qu'on quitte, ni vers un modèle lui aussi épuisé.
  • Un modèle épuisé est mémorisé 1 heure, en mémoire du processus. Pendant ce temps, les messages suivants partent directement vers l'autre modèle, sans retenter le premier. Un redémarrage de CsAgent efface cette mémoire.

Il n'existe pas d'option en ligne de commande pour la bascule : seule la variable d'environnement la règle. Les options --model, --code-model, --chat-model et --endpoint fixent les modèles utilisés et, par ce biais, influencent la bascule.

set CSAGENT_FALLBACK_MODEL=openweight-large
csagent --max-retries 4

set CSAGENT_FALLBACK_MODEL=off
csagent

Quand tout échoue

CsAgent affiche API error: API 429: … suivi d'un conseil, puis arrête la tâche.

  • Quota journalier épuisé : « The daily token quota is used up: retrying is useless until it resets. Wait for the reset, or use another model (--model) or endpoint (--endpoint). »
  • 429 qui persiste après toutes les tentatives : « The API still answers 429 (rate limit) after the retries. Wait a little and try again, or send less text per request. »

Les messages peuvent apparaître traduits selon la langue.

Limites actuelles

  • Pas d'affichage pendant l'attente : l'interface peut sembler figée jusqu'à 70 secondes sans message.
  • Pas de comptage préventif : CsAgent ne sait pas qu'il approche de la limite, il la découvre par un refus.
  • Limite mal identifiée : un 429 journalier dont le texte ne contient aucun des mots reconnus est traité comme une limite par minute. Il est alors réessayé jusqu'au bout avant l'échec.
  • Options ignorées en silence : une valeur invalide pour --max-retries ou --retry-delay retombe sur le défaut sans avertissement.
